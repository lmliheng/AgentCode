## 实现记录与两处对 design 的更正

`npx vitest run` **22 文件 / 158 用例全绿**。

**更正一：`read_directory` 并非「无条数上限」。** design.md 的现状表把它记为「仅限深度、无体积上限」，实际它已有 `maxItems: 500`（默认值）。真正的缺口是**体积维度**：返回值是嵌套树，每项还带 `path`/`size`，字符数与行数都不受约束。本次补的是字符 + 行数两个维度，而不是条数。

**更正二：5.1 的前提没有成立，既有测试断言无需改动。** design.md 的 Risks 预测「12 个工具测试直接断言 `validate` / `execute` 的返回值，会受影响，需同步更新」—— 实际未发生。原因在于本实现选择的**执行点**：预算施加在「工具结果序列化为送入模型的消息」这一步，而不是工具自身的返回值上。因此：
- 12 个工具测试与 2 个集成测试**原样通过**，未改一行
- `git diff --stat` 中该目录下的改动全部来自上一个 change（`ds.test.ts` / `ds_provider.test.ts` / `react_loop.test.ts`）
- 代价是工具的 `execute()` 返回值仍持有完整输出，内存占用未随之下降 —— 这一次的 Non-Goal 正是「不做落盘清理与生命周期管理」，若将来需要控制进程内存，应另开变更处理

**其余实现要点：**

- 截断后的内容是**合法 JSON**：不是把截断后的 JSON 片段直接送出（那会变成非法 JSON），而是换成 `{success, error, truncated, originalLength, fullOutputPath, output}` 结构。
- 落盘目录为 `<系统临时目录>/coding-agent-tool-output/<工作区哈希>/`，按工作区区分以免不同项目互相干扰。
- 4.2 的「估算」路径：模型响应未带回用量时，按消息字符数 ÷ 4 粗略推算，来源标记为 `estimated`；`measured` / `estimated` / `unknown` 三种情形各有用例覆盖。
- 1.5 的占位说明目前是**防御性**的：运行时会把「成功且 `data` 为空」的结果替换为占位文本，但现有 12 个工具的 `data` 均非空，因此实际不会触发；用例用一个合成的无输出工具覆盖了该路径。
